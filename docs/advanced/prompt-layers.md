# Prompt Layers

## Overview

When the Agent Orchestrator spawns a session, it assembles a structured system prompt from multiple layers of context. This **prompt composition pipeline** ensures every agent receives the right information — project context, task details, user rules, past learnings, and cross-session memory — in a consistent, layered format.

The system has **two parallel delivery mechanisms**:

1. **Composed prompt** — assembled by `buildPrompt()` from 5 layers, delivered to the agent via the runtime's `sendMessage()` API
2. **CLAUDE.md merge** — merges project rules with provider-specific additions into the worktree's `CLAUDE.md` file, which the agent reads natively

Both mechanisms operate independently and are both non-blocking — failures in either path never prevent session spawn.

**Core prompt builder:** `packages/core/src/prompt-builder.ts`
**CLAUDE.md merge:** `packages/core/src/claudemd-merge.ts`

**Related docs:** [Sessions](../core-concepts/sessions/), [Memory & Learning](../core-concepts/memory-learning/), [Custom Plugin Development](custom-plugins/)

## Layer Architecture

The `buildPrompt()` function assembles up to 6 sections in strict order. Each layer has a config gate that controls whether it's included.

**Source:** `packages/core/src/prompt-builder.ts`

### PromptBuildConfig

The input to `buildPrompt()` carries all layer data:

```typescript
interface PromptBuildConfig {
  project: ProjectConfig;         // Full project config
  projectId: string;              // Key in the projects map
  issueId?: string;               // e.g. "INT-1343", "#42"
  issueContext?: string;          // Pre-fetched from tracker
  storyContext?: string;          // From sprint-status.yaml + story file
  userPrompt?: string;            // Explicit --prompt argument
  learnings?: SessionLearning[];  // Past session learnings
  crossSessionMemory?: string;    // Pre-formatted memory layer
}
```

### Layer Assembly Order

```
buildPrompt(config)
  ├─ Layer 1: BASE_AGENT_PROMPT           (always, when composing)
  ├─ Layer 2: buildConfigLayer()           (always, when composing)
  ├─ Layer 3: readUserRules()              (if agentRules or agentRulesFile set)
  ├─ Layer 4: buildLearningsLayer()        (if learning.injectInPrompts enabled)
  ├─ Layer 5: crossSessionMemory           (if learning.crossSessionMemory enabled)
  └─ Final:  userPrompt                    (if --prompt argument provided)
```

If no layer has content (no issue, no story, no rules, no user prompt), `buildPrompt()` returns `null` — preserving backward compatibility for bare launches.

| Layer | Heading | Config Gate | Source |
|-------|---------|-------------|--------|
| 1. Base | (none, inline) | Always (when composing) | `prompt-builder.ts:22` |
| 2. Config | `## Project Context`, `## Task`, `## Issue Details`, `## Story Context`, `## Automated Reactions` | Always (when composing) | `prompt-builder.ts:76` |
| 3. Rules | `## Project Rules` | `project.agentRules` or `project.agentRulesFile` | `prompt-builder.ts:129` |
| 4. Learnings | `## Lessons from Past Sessions` | `project.learning.injectInPrompts` | `prompt-builder.ts:211` |
| 5. Memory | `## Cross-Session Knowledge` | `project.learning.crossSessionMemory` | `memory-bridge.ts:392` |
| Final | `## Additional Instructions` | `--prompt` CLI argument | `prompt-builder.ts:199` |

## Layer 1: Base Agent Prompt

A constant string containing foundational instructions that every managed agent receives.

**Source:** `packages/core/src/prompt-builder.ts:22-40`

```typescript
export const BASE_AGENT_PROMPT = `You are an AI coding agent managed by the Agent Orchestrator (ao).

## Session Lifecycle
- You are running inside a managed session. Focus on the assigned task.
- When you finish your work, create a PR and push it. The orchestrator will handle CI monitoring and review routing.
- If CI fails, the orchestrator will send you the failures — fix them and push again.
- If reviewers request changes, the orchestrator will forward their comments — address each one, push fixes, and reply to the comments.

## Git Workflow
...
## PR Best Practices
...`;
```

The full constant also includes sections for **Git Workflow** and **PR Best Practices** (omitted above for brevity). This layer is always included whenever `buildPrompt()` produces a non-null result.

## Layer 2: Config Context

Generated by `buildConfigLayer()`, this layer injects project-specific context extracted from the orchestrator config.

**Source:** `packages/core/src/prompt-builder.ts:76-123`

### Sections Produced

| Section | Condition | Config Fields |
|---------|-----------|---------------|
| `## Project Context` | Always | `project.name`, `projectId`, `project.repo`, `project.defaultBranch`, `project.tracker?.plugin` |
| `## Task` | `issueId` is set | `issueId` |
| `## Issue Details` | `issueContext` is set | Pre-fetched from `tracker.generatePrompt()` |
| `## Story Context` | `storyContext` is set | Pre-formatted from sprint-status.yaml + story file |
| `## Automated Reactions` | Reactions with `auto: true` and `action: "send-to-agent"` | `project.reactions` |

The tracker context is fetched during the spawn flow in `session-manager.ts` — if an `issueId` is provided and a tracker plugin is available, `tracker.generatePrompt()` fetches the full issue description and comments.

## Layer 3: User Rules

Custom rules that project maintainers define to guide agent behavior.

**Source:** `packages/core/src/prompt-builder.ts:129-149`

The `readUserRules()` function reads from two config sources:

1. **`project.agentRules`** — inline string in the config
2. **`project.agentRulesFile`** — path to a file, resolved relative to `project.path`

```yaml
projects:
  my-service:
    agentRules: |
      Always write tests for new functions.
      Use vitest, not jest.
    agentRulesFile: ".omc/agent-rules.md"
```

Both sources are concatenated (inline first, then file content). If neither is set, Layer 3 is omitted entirely. File-not-found is silently ignored.

## Layer 4: Session Learnings

Injects failure patterns from past sessions to help agents avoid repeating mistakes. The filtering pipeline has **two stages** with different semantics.

**Source:** `packages/core/src/prompt-builder.ts:211-238`, `packages/core/src/session-learning.ts`

### Two-Stage Filtering Pipeline

```
Session Manager spawn flow
  └─ selectRelevantLearnings()  — pre-filters to outcome === "failed" only
       └─ buildLearningsLayer() — formats, re-filters with outcome !== "completed"
            └─ Formatted ## Lessons from Past Sessions section
```

| Stage | Function | Filter | Purpose |
|-------|----------|--------|---------|
| Pre-filter | `selectRelevantLearnings()` | `outcome === "failed"` | Strict: only failed sessions |
| Format-time | `buildLearningsLayer()` | `outcome !== "completed"` | Broad: excludes only "completed" |

The pre-filter is stricter. In the normal spawn flow, `selectRelevantLearnings()` runs first and reduces the set to failed outcomes only, so `buildLearningsLayer()` effectively receives only `"failed"` entries. The broader `!== "completed"` filter in `buildLearningsLayer()` acts as a safety net — if called directly with unfiltered learnings, it would include `"abandoned"` and `"blocked"` outcomes as well.

### buildLearningsLayer()

Formats past session failures as actionable guidance:

```
## Lessons from Past Sessions

In previous similar work, these issues were encountered:

1. **62-8-fix-null-pointer** (failed) — errors: TypeError, NullReference
   Domains: validation, error-handling | Duration: 12m
```

### selectRelevantLearnings()

Pre-filters and prioritizes learnings before passing to `buildLearningsLayer()`:

| Filter | Rule |
|--------|------|
| Failures only | `outcome === "failed"` (strict) |
| Domain matching | Entries whose `domainTags` overlap with the current story's tags are sorted first |
| Recency | Newest `capturedAt` first |
| Limit | Maximum 3 entries (configurable via `limit` parameter) |

**Config gate:** `project.learning.injectInPrompts` must be `true`.

```yaml
projects:
  my-service:
    learning:
      injectInPrompts: true
```

### SessionLearning Type

Each learning entry contains:

```typescript
interface SessionLearning {
  sessionId: string;
  agentId: string;
  storyId: string;
  projectId: string;
  outcome: string;           // "completed" | "failed" | ...
  durationMs: number;
  retryCount: number;
  filesModified: string[];
  testsAdded: number;
  errorCategories: string[];
  domainTags: string[];
  completedAt: string;
  capturedAt: string;
}
```

## Layer 5: Cross-Session Memory

Accumulated knowledge shared across sessions working on the same project.

**Source:** `packages/core/src/memory-bridge.ts`

### buildCrossSessionMemoryLayer()

Loads cross-session memory from the project's JSONL store and formats it as a context section:

```
## Cross-Session Knowledge

### Insights
- Prefer execFile over exec for security (from 3 session(s))
- Always add .js extensions in ESM imports (from 5 session(s))

### Conventions
- Use vitest for testing (from 2 session(s))
```

Entries are grouped by type, with each type getting a capitalized heading. Each item shows how many sessions contributed that knowledge.

**Config gate:** `project.learning.crossSessionMemory` must be `true`.

```yaml
projects:
  my-service:
    learning:
      crossSessionMemory: true
```

### Content-Hash Deduplication

Memory entries are deduplicated at two points:

1. **Write-time** — incoming entries are merged by content hash (`MD5(type + ":" + content)`). If a matching entry exists, `sourceSessionIds` are merged and `lastSeenAt` is updated
2. **Read-time** — all JSONL lines are parsed and merged by hash, combining session IDs and reconciling timestamps

### 10MB Rotation

The JSONL storage file (`cross-session-memory.jsonl`) rotates when it reaches 10MB:

- The current file is renamed to `cross-session-memory-{timestamp}.jsonl`
- New entries are appended to a fresh file
- Rotation happens transparently — no data loss

## CLAUDE.md Merge

Parallel to the composed prompt, the orchestrator can merge provider-specific instructions into the worktree's `CLAUDE.md` file. This gives agents access to provider capabilities (delegation patterns, agent catalogs, conventions) through their native file-reading behavior.

**Source:** `packages/core/src/claudemd-merge.ts`

### Merge Format

The merged file follows this structure:

```markdown
<original project CLAUDE.md content preserved verbatim>
---
<!-- Provider: omc -->
## Provider Enhancements (omc)

<provider additions — agent catalog, delegation instructions, conventions>
<!-- /Provider: omc -->
```

### mergeClaudeMd()

```typescript
function mergeClaudeMd(
  existingContent: string,
  providerAdditions: string,
  providerName: string,
): string;
```

Key behaviors:

- **Project content first** — the original CLAUDE.md is always preserved verbatim at the top
- **Provider section appended** — separated by `---` with marked boundaries
- **Idempotent re-merge** — `stripProviderSection()` removes any existing provider section (detected by `<!-- Provider: {name} -->` marker) before appending fresh content. This prevents duplicate sections on session restore or re-spawn
- **Provider name validation** — `performMerge()` validates provider names against `PROVIDER_NAME_RE` (alphanumeric, hyphens, underscores only) to prevent path traversal and marker injection

### performMerge()

Called from the spawn flow after `activeProvider.configure()` succeeds:

```typescript
const mergeResult = await performMerge(workspacePath, activeProvider.name);
```

Steps:
1. Check for provider additions file at `.{providerName}/provider-claude-md.md` in the worktree (e.g., `.omc/provider-claude-md.md` for the default OMC provider)
2. If absent, return `{ merged: false }` — no error
3. Read existing `CLAUDE.md` (defaults to empty if missing)
4. Read provider additions file
5. Call `mergeClaudeMd()` to produce merged content
6. Skip write if no changes detected
7. Write atomically via `writeClaudeMd()` (temp file + rename pattern)
8. Verify merged file exists and contains the provider marker

The merge is wrapped in try/catch — failure never blocks session spawn.

## Delivery Mechanisms

The composed prompt and CLAUDE.md merge are **two separate delivery paths** that operate in parallel:

| Aspect | Composed Prompt | CLAUDE.md Merge |
|--------|----------------|-----------------|
| Delivery | Runtime `sendMessage()` at spawn | File write to worktree |
| Read by | Agent at session start | Agent natively reads file |
| Content type | Structured system prompt | Markdown instructions |
| When applied | Every spawn | After `provider.configure()` succeeds |
| Failure mode | Non-blocking (warning logged) | Non-blocking (warning logged) |
| Idempotent | Re-sent each time | Strips old provider section first |
| Config gate | `buildPrompt()` args | `sessionEnhancement` provider + additions file |

**When to use which:**

- The **composed prompt** is the primary mechanism — it delivers task-specific context (issue details, story context, learnings, memory) that changes per session
- The **CLAUDE.md merge** delivers static provider instructions (agent catalog, delegation patterns) that apply to all sessions in the project

Most sessions receive both — the composed prompt for dynamic context and the CLAUDE.md for provider capabilities.

## Configuration

### Config Fields

All prompt layer behavior is controlled by project-level config in `agent-orchestrator.yaml`:

| Field | Layer | Type | Default | Purpose |
|-------|-------|------|---------|---------|
| `project.agentRules` | Layer 3 | `string` | (none) | Inline rules injected as `## Project Rules` |
| `project.agentRulesFile` | Layer 3 | `string` | (none) | Path to rules file (relative to `project.path`) |
| `project.orchestratorRules` | — | `string` | (none) | Orchestrator-specific rules (not injected into agent prompt) |
| `project.learning.injectInPrompts` | Layer 4 | `boolean` | `false` | Enable failure learnings injection |
| `project.learning.crossSessionMemory` | Layer 5 | `boolean` | `false` | Enable cross-session memory injection |
| `project.sessionEnhancement` | CLAUDE.md | `SessionEnhancementConfig` | (none) | Provider config driving CLAUDE.md merge |

### Layer 4 and 5 Opt-In

Learnings and cross-session memory are **off by default** — they must be explicitly enabled per project:

```yaml
projects:
  my-service:
    learning:
      injectInPrompts: true       # Layer 4: inject past failures
      crossSessionMemory: true    # Layer 5: inject shared knowledge
```

Both features have safeguards:
- Learnings are limited to 3 entries, filtered to failures only, and sorted by domain relevance
- Cross-session memory uses content-hash dedup and 10MB rotation to prevent unbounded growth

## Config Examples

### Basic Prompt Layer Config

Enable user rules for a project:

```yaml
projects:
  payment-service:
    name: "Payment Service"
    repo: "org/payment-service"
    path: "~/projects/payment-service"
    defaultBranch: main
    agentRules: |
      Always validate input at API boundaries.
      Use Zod schemas for all request validation.
      Never log sensitive data (tokens, PII).
```

### Rules from File

Load rules from a separate file — useful for complex rule sets:

```yaml
projects:
  payment-service:
    agentRulesFile: ".omc/agent-rules.md"
```

The file is resolved relative to `project.path`. Both `agentRules` and `agentRulesFile` can be used together (inline first, then file content appended).

### Full Learning + Memory Config

Enable all prompt layers with session enhancement:

```yaml
projects:
  critical-service:
    name: "Critical Service"
    repo: "org/critical-service"
    path: "~/projects/critical-service"
    defaultBranch: main
    agentRules: |
      Run the full test suite before marking tasks complete.
      Never skip type checking.
    learning:
      injectInPrompts: true
      crossSessionMemory: true
    sessionEnhancement:
      provider: omc
      config:
        autoInstall: true
        mergeStrategy: append
```

### Per-Project Override

Different projects can have different prompt layer configurations:

```yaml
# Global defaults
projects:
  lib-shared:
    name: "Shared Library"
    repo: "org/lib-shared"
    path: "~/projects/lib-shared"
    defaultBranch: main

  critical-service:
    name: "Critical Service"
    repo: "org/critical-service"
    path: "~/projects/critical-service"
    defaultBranch: main
    agentRules: |
      Zero tolerance for type errors.
      All functions must have explicit return types.
    learning:
      injectInPrompts: true
      crossSessionMemory: true
    sessionEnhancement:
      provider: omc
      hookProfile:
        phases:
          - preCompact
          - postCompact
        enabledHooks:
          - notepad
          - projectMemory
```
